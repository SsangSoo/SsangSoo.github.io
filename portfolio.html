CASE 01

AWS RDS 로그 수집 실패 — IAM Role 적용 방식 차이 발견

2026.10 ~ 2026.11APM 솔루션 엔지니어대기업 고객사 (AWS 운영 환경)
  • 와탭 DBXC 에이전트
  • AWS IAM
  • STS AssumeRole
  • CloudWatch Logs
  • RDS PostgreSQL
  • 로그 분석

결과 — 원인을 특정해 벤더(와탭랩스)에 전달했고, 벤더가 이를 제품 개선에 반영했습니다. 같은 문제를 겪던 다른 고객사 사례까지 이어져 AWS 계정 간(크로스 어카운트) 수집 기능 개발이 진행됐습니다.

상황

고객사는 AWS RDS(PostgreSQL)를 와탭 DBXC 에이전트로 모니터링하고 있었습니다. DBXC 에이전트는 와탭 DB 모니터링의 클라우드용 에이전트로, EC2 같은 서버에 설치되어 AWS CloudWatch API로 RDS의 메트릭과 DB 로그를 가져옵니다.

이 에이전트에서 메트릭은 정상으로 수집되는데 DB 로그만 수집되지 않는 문제가 발생했습니다. 에이전트 설정에는 수집용 IAM Role(AssumeRole 대상)이 지정되어 있었고, 그 Role에는 로그 조회 권한이 포함된 관리형 정책이 붙어 있었습니다.

참고 문서: 와탭 DBXC 에이전트 설치 및 사용 · DBXC 로그 수집 설정 (WhaTap Docs)

분석 과정

  1. 권한이 있는데도 실패한다는 점에서 "권한 부족"이 아니라 "다른 주체로 호출하고 있다"는 가설을 세우고 에이전트 로그를 확인했습니다.
  2. 에러 로그의 호출 주체가 설정한 수집용 Role이 아니라, DBXC 에이전트가 설치된 EC2 서버 자체의 IAM Role(인스턴스 Role)이라는 점을 발견했습니다. 
    AccessDeniedException: User: arn:aws:sts::<ACCOUNT>:assumed-role/<collector-ec2-role>/<instance-id>
is not authorized to perform: logs:FilterLogEvents on resource: ...:log-group:/aws/rds/cluster/<cluster>/postgresql
  3. 즉 메트릭 수집은 설정된 Role을 AssumeRole해서 호출하지만, 로그 수집은 AssumeRole 없이 EC2 기본 자격 증명으로 호출하고 있었습니다. 에러 로그, 정책 구성, 에이전트 버전, 계정 구성을 정리해 벤더에 전달했고, 벤더도 같은 원인으로 확인했습니다.

해결

  • 임시 조치: 에이전트가 설치된 EC2와 RDS가 같은 AWS 계정이라는 점을 확인한 뒤, EC2 Role에 logs:FilterLogEvents, logs:DescribeLogGroups 권한만 최소로 추가해 바로 수집되도록 안내했습니다.
  • 근본 해결: 로그 수집에도 설정된 Role을 적용해 달라고 벤더에 요청하고 진행 상황을 계속 확인했습니다. 벤더가 이를 제품에 반영해 로그도 설정된 수집용 Role로 가져오게 됐고, 덕분에 임시로 추가했던 EC2 Role 권한을 다시 제거할 수 있게 됐습니다.

배운 점

"권한이 있는데 거부된다"는 상황에서는 정책 내용보다 실제로 호출한 주체(Principal)를 먼저 확인해야 한다는 것을 배웠습니다. 에러 메시지의 ARN 한 줄이 원인을 가장 정확하게 알려줬습니다.

CASE 02

Keycloak SAML 2.0 SSO 연동 — Nginx 502와 인증 만료 오류 해결

2026.10APM 솔루션 엔지니어금융권 고객사 연동 지원
  • Keycloak
  • SAML 2.0
  • Nginx
  • Docker Compose
  • Spring Security
  • NTP

결과 — 고객사 구성(Nginx + Keycloak + 모니터링 서버)을 Docker로 재현해 연동 절차를 검증했고, 그 과정에서 만난 두 가지 장애의 원인과 해결 방법을 가이드로 정리해 고객사 연동에 적용했습니다.

상황

고객사가 Nginx 리버스 프록시 뒤의 Keycloak을 IdP로 사용해 모니터링 솔루션에 SAML 2.0 SSO를 적용하려 했습니다. 벤더 가이드는 다른 Keycloak 버전 기준이라 메뉴 구성이 달라서, 그대로 따라 할 수 없었습니다.

분석 및 해결

  1. 재현 환경 구성 — Docker Compose로 Nginx와 Keycloak(10.0.2)을 띄우고, 프록시 헤더(X-Forwarded-*)와 프론트 URL을 고객사 구성과 같게 맞췄습니다. Realm 생성부터 IdP 메타데이터 등록, SAML Client 서명 옵션 설정까지 직접 수행하며 절차를 검증했습니다.
  2. 문제 ① 로그인 직후 502 Bad Gateway — 브라우저에는 502만 보여서, Nginx 에러 로그를 확인했습니다. 
    upstream sent too big header while reading response header from upstream
    SAML 응답 과정에서 Keycloak이 보내는 응답 헤더가 Nginx 기본 프록시 버퍼보다 커서 생긴 문제였습니다. 프록시 버퍼 크기를 늘려 해결했습니다. 
    proxy_buffers           4 256k;
proxy_busy_buffers_size 256k;   # + proxy_buffer_size 상향
  3. 문제 ② 로그인 화면은 넘어가는데 인증이 실패 — 화면에는 단서가 없어서, 모니터링 서버의 SSO 디버그 로그(debug_sso=true)를 켜고 원인을 찾았습니다. 
    Saml2AuthenticationException: Invalid assertion [...]:
Assertion '...' with NotOnOrAfter condition of '...' is no longer valid
    SAML Assertion의 유효 시간이 이미 지난 것으로 판정되고 있었습니다. 확인해 보니 모니터링 서버는 시간 동기화가 되어 있었지만 Keycloak 서버는 시각이 어긋나 있었습니다. 서버 간 시간을 동기화하자 정상 로그인됐습니다.

배운 점

  • 서버 간 시간 동기화는 연동의 기본 전제입니다. SAML처럼 인증 정보에 유효 시간을 담아 검증하는 방식은, 서버끼리 시각이 조금만 어긋나도 정상 요청을 만료된 것으로 판정합니다. 화면이나 일반 로그에는 원인이 드러나지 않아 가장 찾기 어려웠던 문제였습니다.
  • Nginx가 HTTP 응답을 중계할 때 쓰는 버퍼에는 크기 한계가 정해져 있고, 설정으로 늘릴 수 있습니다. 응답 헤더가 기본 버퍼(proxy_buffer_size)보다 크면 Nginx는 응답을 전달하지 못하고 502를 반환합니다. 이 경우 proxy_buffer_size, proxy_buffers, proxy_busy_buffers_size를 키워서 해결할 수 있다는 것을 배웠습니다.

CASE 03

생성형 AI로 Go APM 계측 검증 — 제품 버그 발견

2026.11APM 솔루션 엔지니어Go 애플리케이션 고객사 지원
  • 생성형 AI
  • Go
  • Gin · Echo · Fiber
  • GORM · sqlx
  • gRPC · Kafka
  • 자동 계측

결과 — 생성형 AI로 17개 라이브러리를 쓰는 검증용 Go 앱을 빠르게 만들어 자동 계측 도구를 검증했습니다. 그 과정에서 --error-tracking 옵션의 비정상 동작을 발견했고, 벤더가 이를 제품 버그로 확인했습니다.

상황

와탭 Go APM은 whatap-go-inst go build처럼 빌드 명령을 감싸서, 컴파일할 때 모니터링 코드를 주입하는 방식입니다. 고객사가 쓰는 프레임워크와 라이브러리에서 계측이 잘 되는지 확인하려면, 그 라이브러리들을 실제로 쓰는 Go 애플리케이션이 필요했습니다. 하지만 Go는 주력 언어(Java)가 아니어서, 검증용 앱을 처음부터 직접 만들기에는 시간이 많이 드는 상황이었습니다.

AI를 활용한 검증 과정

  1. AI로 검증용 샘플 앱 생성 — 확인해야 할 라이브러리 목록을 정리해 생성형 AI에게 샘플 앱과 테스트 코드를 만들게 했습니다. 웹 프레임워크 6종(net/http, Gin, Echo, Fiber, chi, gorilla/mux), DB 접근 4종(database/sql, sqlx, GORM v1/v2), Redis, MongoDB, gRPC, Kafka(sarama), Kubernetes client까지 17개 의존성을 담았습니다.
  2. 결과는 실제 빌드로만 판단 — AI가 만든 코드를 그대로 믿지 않고, go build, go test, remove 명령을 직접 실행했습니다. 파일마다 계측 코드가 주입됐는지, 테스트가 통과하는지 출력으로 하나씩 확인했습니다. 이 과정에서 문서에 있던 inject 명령이 이미 제거됐고, 설정 파일의 preset 항목도 지원하지 않는다는 점을 확인해 정리했습니다.
  3. 이상 동작 발견과 AI를 활용한 원인 분석 — 에러 추적 코드를 자동으로 주입하는 --error-tracking 옵션을 켜면 빌드가 실패하고, 계측된 파일이 0개였습니다. 
    $ whatap-go-inst --error-tracking go build -o app .
go: error obtaining buildID for go tool compile: exit status 1
📁 Total: 0 files
    낯선 Go 빌드 에러를 AI와 함께 해석하며 가능한 원인을 좁혔습니다. 그리고 같은 코드에서 옵션만 바꿔 다시 빌드해서, 내 코드나 환경이 아니라 옵션 자체에서 생기는 문제라는 것을 직접 확인했습니다.
  4. AI로 재현 절차와 문의 내용 정리 — 재현 명령, 기대 결과와 실제 결과, 옵션 유무 비교를 AI로 정리해 벤더에 문의했습니다. 벤더가 이를 제품 버그로 확인했습니다.

AI와 역할 나누기

  • AI에게 맡긴 일: 샘플 앱과 테스트 코드 생성, 낯선 에러 메시지 해석, 재현 절차와 문의 내용 정리
  • 직접 한 일: 무엇을 검증할지 정하기, 실제 빌드와 실행, 결과 판단, 원인 확정

배운 점

주력 언어가 아니어도 생성형 AI를 쓰면 검증 환경을 빠르게 갖출 수 있다는 것을 경험했습니다. 다만 AI가 만든 코드와 설명은 출발점일 뿐이고, 최종 판단은 실제 빌드 결과와 로그로 해야 한다는 원칙을 지켰기 때문에 제품 버그까지 찾아낼 수 있었습니다.

CASE 04

고객사 재현용 폐쇄망 테스트 환경 구축

2026APM 솔루션 엔지니어사내 테스트 환경
  • Rocky Linux
  • Kubernetes
  • Harbor
  • Docker
  • Prometheus

결과 — 외부망이 차단된 폐쇄망 고객사가 많아서, 비슷한 조건의 테스트 환경을 직접 구성했습니다. 고객사에서 생긴 문제를 사내에서 먼저 재현하고 검증한 뒤 대응할 수 있게 됐습니다.

구성한 것

  • 컨테이너 레지스트리(Harbor 2.14) — 외부망 레지스트리를 쓸 수 없는 환경을 가정해 사설 레지스트리를 구축했습니다. 설정 파일 전체를 항목별로 분석해 문서화했고, 이미지 취약점 스캐너(Trivy)를 폐쇄망에서 쓰려면 어떤 옵션이 필요한지도 정리했습니다(skip_update, offline_scan).
  • Kubernetes 테스트 클러스터 — 클러스터를 구성해 컨테이너 모니터링 에이전트 배포를 실습했습니다. 특정 노드에만 DaemonSet을 배포하는 방법과 kubeconfig 인증서 오류 해결 과정을 정리했습니다.
  • 오프라인 패키지 설치 절차 — 외부망이 되는 곳에서 의존성까지 내려받고(dnf --downloadonly), 폐쇄망에서는 저장소를 끈 채 설치하는(localinstall --disablerepo=*) 절차를 만들었습니다.
  • Keycloak SSO 재현 환경 — Docker Compose 기반으로 구성했습니다(CASE 02).
  • OpenMetrics 수집 검증 — Prometheus 형식(OpenMetrics)으로 노출되는 메트릭을 수집하는 파이프라인을 만들고, 모니터링 에이전트로 연동되는지 확인했습니다.

일하는 방식

설정 파일과 명령마다 "이 옵션이 왜 필요한지"를 주석으로 남겨 팀이 함께 쓰는 문서로 만들었습니다. 설정 초안을 쓸 때는 생성형 AI를 활용했고, 실제 실행 결과와 오류 로그로 검증한 뒤 수정했습니다.

CASE 05

데이터 마이그레이션 INSERT 문 생성 자동화 — 작업 시간 약 85% 단축

2024.06 ~ 2025.07백엔드 개발대형 가전 기업 해외 사이트 구축 (AEM)
  • Java
  • Excel 함수
  • SQL
  • 데이터 마이그레이션
  • 업무 자동화

결과 — 컬럼 타입만 지정하면 행마다 INSERT 문을 만들어주는 엑셀 함수를 생성하는 Java 메서드를 만들었습니다. 테이블당 INSERT 문 작성 시간이 약 20분에서 3분으로(약 85%) 줄었고, 따옴표 처리 같은 수작업 실수도 없앴습니다.

상황

고객사에서 받은 엑셀 데이터를 DB로 옮기는 작업이었습니다. 이관 대상은 약 200개 테이블, 30~40만 건이었고, 한 테이블에 수천~2만 5천 건이 들어 있었습니다. 운영 반영은 작업 절차를 기록한 작업 계획서대로 진행해야 해서, 최종 결과물은 INSERT 문이어야 했습니다.

더 나은 방법을 찾아간 과정

  1. 멀티커서로 직접 작성 — DB 툴의 멀티커서로 INSERT 문을 만들었습니다. 그런데 200건을 넣는 데 시행착오를 포함해 4~5시간이 걸렸습니다. 데이터가 많아지면 툴이 느려졌고, 텍스트 안의 작은따옴표(')를 ''로 일일이 바꿔야 하는 문제도 있었습니다.
  2. 엑셀 함수로 전환 — 2번 행에 INSERT 문을 만드는 함수를 한 번 써 두고 밑으로 끌어내리는 방식으로 바꿔 속도가 크게 올랐습니다. 하지만 컬럼이 많은 테이블에서는 셀 참조를 하나하나 잇고, 문자/숫자 타입에 따라 따옴표를 다르게 넣어야 해서 함수 한 줄 만드는 데도 시간이 오래 걸리고 실수가 잦았습니다.
  3. CSV 적재 검토 — CSV로 바로 적재하면 가장 빨랐지만, 운영 반영은 INSERT 문으로 해야 해서 쓸 수 없었습니다. 그래서 반영 방식(INSERT 문)은 지키면서, 반복되는 함수 작성을 자동화하는 쪽으로 방향을 정했습니다.
  4. 엑셀 함수를 만들어주는 Java 메서드 개발 — 테이블명, 컬럼 수, 숫자 타입 열만 넣으면 함수가 완성되도록 만들었습니다.
    • 숫자 타입은 그대로, 빈 셀은 NULL로 넣습니다. 문자 타입은 작은따옴표로 감싸고, 값 안의 '는 SUBSTITUTE로 ''로 바꿉니다.
    • 컬럼이 26개를 넘으면 엑셀처럼 Z 다음 AA, AB…로 이어지도록 열 이름을 계산합니다.
    • 컬럼명은 A$1처럼 1행을 고정해서, 함수를 밑으로 끌어내려도 계속 1행의 컬럼명을 봅니다.
    generate("member", 4, Set.of("A", "B"))   // A, B는 숫자 타입

="INSERT INTO member ("&A$1&", "&B$1&", "&C$1&", "&D$1&") values ("
 &IF(A2="","NULL",A2)&", "&IF(B2="","NULL",B2)&", "
 &"'"&SUBSTITUTE(C2,"'","''")&"'"&", "&"'"&SUBSTITUTE(D2,"'","''")&"'"&");"
    만들어진 함수를 2행에 붙여넣고 밑으로 끌어내리면 행마다 INSERT 문이 하나씩 완성됩니다.

배운 점

가장 빠른 방법(CSV)이 항상 정답은 아니었습니다. 운영 반영 방식이라는 제약 안에서 반복되는 부분을 찾아 코드로 자동화하는 것이 실제로 효율을 내는 방법이었습니다. 또 지금 방식이 비효율적이라는 것을 스스로 알아차리고 계속 더 나은 방법을 찾아가는 과정 자체가 중요하다는 것을 배웠습니다. · 관련 글

CASE 06

사내 그룹웨어 복지포인트 갱신 오류 — 싱글톤 빈에 고정된 날짜

2025.01백엔드 개발 · 유지보수사내 그룹웨어
  • Java
  • Spring
  • @Component
  • 싱글톤 빈
  • LocalDate
  • 로그 분석

결과 — 매년 1월에만 드러나던 복지포인트 갱신 오류의 원인이 스프링 싱글톤 빈의 필드에 고정된 날짜라는 것을 찾아냈습니다. 날짜를 호출할 때마다 계산하도록 바꿔 해결했습니다.

상황

사내 그룹웨어의 복지포인트는 매달 11일에 갱신됩니다. 그런데 1월 11일에 포인트가 갱신되지 않았고, 백엔드가 내려주는 값도 이상했습니다. 포인트 계산 로직은 @Component 클래스에 있었고, 1월인지 아닌지에 따라 계산 방식이 나뉘어 있었습니다.

분석 과정

  1. 로그 확인 — 계산에 쓰인 기준 날짜를 로그로 확인해 보니, 오늘 날짜가 아니라 2024년 12월이었습니다.
  2. 날짜가 어디서 오는지 추적 — 기준 날짜는 클래스의 인스턴스 필드에 LocalDate.now()로 저장된 값이었습니다. 
    @Component
public class Util {
    private final LocalDate today = LocalDate.now();   // 빈이 만들어질 때 한 번만 계산된다
    ...
    calculation(today);
}
  3. 원인 확정 — @Component 클래스는 애플리케이션이 시작될 때 싱글톤 빈으로 한 번 만들어집니다. 그래서 today에는 서버를 마지막으로 띄운 날짜(12월)가 고정된 채로 남아 있었습니다. 계산이 "1월인지 아닌지"로만 갈리기 때문에, 다른 달에는 결과가 같아서 드러나지 않다가 1월이 되어서야 문제가 보였습니다.

해결

날짜를 필드에 저장하지 않고, 필요할 때마다 메서드를 호출해 계산하도록 바꿨습니다. 기존 코드의 흐름은 그대로 두고 호출부만 바꿔 변경 범위를 최소화했습니다.

private static LocalDate today() {
    return LocalDate.now();
}
...
calculation(today());   // 호출할 때마다 오늘 날짜

배운 점

싱글톤 빈의 필드는 빈이 만들어질 때 한 번만 초기화됩니다. 그래서 시간처럼 계속 바뀌는 값을 필드에 두면, 서버를 띄운 시점에 멈춰 버립니다. 시간에 의존하는 값은 사용하는 시점에 계산해야 한다는 것을 배웠습니다. · 관련 글

CASE 07

와탭 알림 플러그인 개발 — 고객사별 알림 연동 (진행 중)

2025.07 ~ 현재APM 솔루션 엔지니어금융권 등 다수 고객사
  • Java
  • 와탭 알림 플러그인
  • Slack Webhook
  • JDBC
  • REST API
  • 설정 기반 설계

결과 — 와탭 수집서버의 알림 플러그인 구조를 활용해, 고객사마다 다른 알림 요구(Slack 채널 분리, 사내 SMS·메시징 시스템 연동, 별도 경로 기록)를 Java 플러그인으로 구현했습니다. 지금도 고객사 요청에 맞춰 계속 기능을 더하고 다듬고 있습니다.

배경

와탭 수집서버는 알림이 발생하면 플러그인 파일(CustomSenderPlug.x)에 작성한 Java 코드를 실행합니다. 플러그인에서는 알림 제목, 메시지, 레벨, 제품 타입, 이벤트 수신 태그 같은 정보를 받을 수 있습니다. 기본 알림 채널만으로는 고객사의 운영 방식에 맞추기 어려워서, 이 구조를 이용해 고객사별 연동을 만들어 왔습니다.

구현한 것

  1. 공통 유틸 라이브러리 — 플러그인마다 반복되는 HTTP 호출, 문자열·리스트 검증, 알림 레벨별 색상 지정을 별도 Java 유틸 jar로 분리했습니다. 플러그인 코드는 연동 로직에만 집중할 수 있게 했습니다.
  2. 태그별 Slack 채널 라우팅 — 고객사는 알림을 담당 팀별로 다른 Slack 채널에서 받고 싶어 했습니다. 와탭에서는 알림 설정에 이벤트 수신 태그를 붙일 수 있고, 플러그인은 그 태그 목록을 받을 수 있습니다. 또 플러그인 안에서 알림 관련 conf의 값을 읽어올 수 있다는 점을 활용했습니다. 그래서 "어떤 태그를 어느 채널로 보낼지"는 conf에 두고, 플러그인은 그 규칙대로 보내기만 하도록 설계했습니다.
    • conf 키 규칙 — custom_alert_tag_{태그명}, custom_alert_type_{제품 타입} 형식의 키에 Slack Webhook URL을 넣습니다. _default 키는 모든 알림을 함께 받는 전체 채널입니다.
    • 라우팅 규칙 — 알림에 태그가 있으면 태그마다 매핑된 채널(+ 전체 채널)로 보내고, 태그가 없으면 제품 타입(서버, DB 등)별 채널(+ 전체 채널)로 보냅니다. 태그가 있는 알림을 우선하는 구조입니다.
    • 메시지 — 알림 제목과 내용을 Slack 메시지로 만들고, 알림 레벨(위험/경고 등)에 따라 메시지 색을 다르게 지정합니다.
    # 알림 관련 conf — 태그/타입별 Slack 채널 (값만 바꾸면 라우팅이 바뀐다)
custom_alert_tag_default=https://hooks.slack.com/services/...   # 주석 처리하면 전체 채널로는 안 보냄
custom_alert_tag_groupA=https://hooks.slack.com/services/...
custom_alert_tag_groupB=https://hooks.slack.com/services/...
custom_alert_type_SMS=https://hooks.slack.com/services/...
    // 플러그인 핵심 흐름 (요약)
List tags = $box.receiverValues;                       // 알림에 붙은 이벤트 수신 태그
if (태그가 없으면) {
    urls.add(getConfigString("custom_alert_type_default"));
    urls.add(getConfigString("custom_alert_type_" + $product));       // 제품 타입별 채널
} else {
    urls.add(getConfigString("custom_alert_tag_default"));
    for (tag : tags) urls.add(getConfigString("custom_alert_tag_" + tag));   // 태그별 채널
}
// 값이 비어 있는 키는 건너뛰고, 모인 URL마다 Slack 메시지 전송
    검증 — 실제 장애를 기다리지 않고 알림 수신 테스트로 경우마다 확인했습니다. 태그 1개면 해당 채널 + 전체 채널, 태그 n개면 n+1개 채널, 전체 채널 키를 주석 처리하면 해당 채널에만, 태그가 없으면 제품 타입 채널 + 전체 채널로 가는 것을 확인했습니다. 태그명은 conf 키와 정확히 일치해야 하고 영문과 _, -만 쓰는 것을 권장한다는 규칙과 함께, 고객사가 직접 채널을 추가할 수 있도록 가이드로 정리했습니다.
  3. 고객사 SMS 시스템 연동 — 알림이 오면 고객사 SMS 발송 시스템의 DB 테이블에 JDBC(PreparedStatement)로 발송 데이터를 넣습니다. DB 계정 정보는 평문으로 두지 않고, 수집서버의 암호화 도구로 암호화해 알림 관련 conf에 둔 뒤, 플러그인에서 읽어와 복호화해 씁니다.
  4. 고객사 사내 메시징 API 연동 — 알림 제목에 담긴 환경 구분(개발/QA/운영/DR)에 따라 전송 대상을 나눠 고객사 사내 메시징 API를 호출합니다. 알림 처리가 멈추지 않도록 호출에 타임아웃을 두었습니다.
  5. 특정 이벤트를 별도 경로에 기록 (진행 중) — 특정 알림만 평소와 다른 경로에 파일로 남기고 싶다는 요청을 받았습니다. 고객사의 기존 플러그인 파일부터 받아 구조를 확인한 뒤, 태그 기반과 이벤트 제목 키워드 기반 두 가지 방식을 테스트 환경에서 구현해 제안했습니다. 태그를 여러 개 걸면 같은 이벤트가 여러 경로에 기록될 수 있다는 주의점도 함께 안내했습니다.

일하는 방식

  • 바뀌는 값은 설정으로 — 채널 URL, 수신 대상, 계정 정보처럼 고객사마다 다른 값은 알림 관련 conf로 빼서, 같은 플러그인을 여러 고객사에 재사용할 수 있게 했습니다.
  • 먼저 확인하고, 선택지를 드리기 — 고객사의 현재 구성을 먼저 확인하고, 가능한 방식을 장단점과 함께 제안한 뒤 고객사가 고른 방식으로 구성합니다.
