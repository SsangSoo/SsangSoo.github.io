CASE 01

AWS RDS 로그 수집 실패 — IAM Role 적용 방식 차이 발견

2026.10 ~ 2026.11APM 솔루션 엔지니어대기업 고객사 (AWS 운영 환경)
  • 와탭 DBXC 에이전트
  • AWS IAM
  • STS AssumeRole
  • CloudWatch Logs
  • RDS PostgreSQL
  • 로그 분석

결과 — 원인을 특정해 벤더(와탭랩스)에 전달했고, 벤더가 이를 반영해 제품을 수정한 와탭 DBXC 에이전트 0.7.1을 배포했습니다. 같은 문제를 겪던 다른 고객사 사례까지 이어져 AWS 계정 간(크로스 어카운트) 수집 기능 개발이 진행됐습니다.

상황

고객사는 AWS RDS(PostgreSQL)를 와탭 DBXC 에이전트로 모니터링하고 있었습니다. DBXC 에이전트는 와탭 DB 모니터링의 클라우드용 에이전트로, EC2 같은 서버에 설치되어 AWS CloudWatch API로 RDS의 메트릭과 DB 로그를 가져옵니다.

이 에이전트에서 메트릭은 정상으로 수집되는데 DB 로그만 수집되지 않는 문제가 발생했습니다. 에이전트 설정에는 수집용 IAM Role(AssumeRole 대상)이 지정되어 있었고, 그 Role에는 로그 조회 권한이 포함된 관리형 정책이 붙어 있었습니다.

참고 문서: 와탭 DBXC 에이전트 설치 및 사용 · DBXC 로그 수집 설정 (WhaTap Docs)

분석 과정

  1. 권한이 있는데도 실패한다는 점에서 "권한 부족"이 아니라 "다른 주체로 호출하고 있다"는 가설을 세우고 에이전트 로그를 확인했습니다.
  2. 에러 로그의 호출 주체가 설정한 수집용 Role이 아니라, DBXC 에이전트가 설치된 EC2 서버 자체의 IAM Role(인스턴스 Role)이라는 점을 발견했습니다. 
    AccessDeniedException: User: arn:aws:sts::<ACCOUNT>:assumed-role/<collector-ec2-role>/<instance-id>
is not authorized to perform: logs:FilterLogEvents on resource: ...:log-group:/aws/rds/cluster/<cluster>/postgresql
  3. 즉 메트릭 수집은 설정된 Role을 AssumeRole해서 호출하지만, 로그 수집은 AssumeRole 없이 EC2 기본 자격 증명으로 호출하고 있었습니다. 에러 로그, 정책 구성, 에이전트 버전, 계정 구성을 정리해 벤더에 전달했고, 벤더도 같은 원인으로 확인했습니다.

해결

  • 임시 조치: 에이전트가 설치된 EC2와 RDS가 같은 AWS 계정이라는 점을 확인한 뒤, EC2 Role에 logs:FilterLogEvents, logs:DescribeLogGroups 권한만 최소로 추가해 바로 수집되도록 안내했습니다.
  • 근본 해결: 로그 수집에도 설정된 Role을 적용해 달라고 벤더에 요청하고 진행 상황을 계속 확인했습니다. 벤더가 수정된 DBXC 에이전트 0.7.1을 배포하면서, 설정 한 줄만 추가하면 로그도 수집용 Role로 가져오게 됐습니다. 덕분에 임시로 추가했던 EC2 Role 권한을 다시 제거할 수 있게 됐습니다.

배운 점

"권한이 있는데 거부된다"는 상황에서는 정책 내용보다 실제로 호출한 주체(Principal)를 먼저 확인해야 한다는 것을 배웠습니다. 에러 메시지의 ARN 한 줄이 원인을 가장 정확하게 알려줬습니다.

CASE 02

Keycloak SAML 2.0 SSO 연동 — Nginx 502와 인증 만료 오류 해결

2026.10APM 솔루션 엔지니어금융권 고객사 연동 지원
  • Keycloak
  • SAML 2.0
  • Nginx
  • Docker Compose
  • Spring Security
  • NTP

결과 — 고객사 구성(Nginx + Keycloak + 모니터링 서버)을 Docker로 재현해 연동 절차를 검증했고, 그 과정에서 만난 두 가지 장애의 원인과 해결 방법을 가이드로 정리해 고객사 연동에 적용했습니다.

상황

고객사가 Nginx 리버스 프록시 뒤의 Keycloak을 IdP로 사용해 모니터링 솔루션에 SAML 2.0 SSO를 적용하려 했습니다. 벤더 가이드는 다른 Keycloak 버전 기준이라 메뉴 구성이 달라서, 그대로 따라 할 수 없었습니다.

분석 및 해결

  1. 재현 환경 구성 — Docker Compose로 Nginx와 Keycloak(10.0.2)을 띄우고, 프록시 헤더(X-Forwarded-*)와 프론트 URL을 고객사 구성과 같게 맞췄습니다. Realm 생성부터 IdP 메타데이터 등록, SAML Client 서명 옵션 설정까지 직접 수행하며 절차를 검증했습니다.
  2. 문제 ① 로그인 직후 502 Bad Gateway — 브라우저에는 502만 보여서, Nginx 에러 로그를 확인했습니다. 
    upstream sent too big header while reading response header from upstream
    SAML 응답 과정에서 Keycloak이 보내는 응답 헤더가 Nginx 기본 프록시 버퍼보다 커서 생긴 문제였습니다. 프록시 버퍼 크기를 늘려 해결했습니다. 
    proxy_buffers           4 256k;
proxy_busy_buffers_size 256k;   # + proxy_buffer_size 상향
  3. 문제 ② 로그인 화면은 넘어가는데 인증이 실패 — 화면에는 단서가 없어서, 모니터링 서버의 SSO 디버그 로그(debug_sso=true)를 켜고 원인을 찾았습니다. 
    Saml2AuthenticationException: Invalid assertion [...]:
Assertion '...' with NotOnOrAfter condition of '...' is no longer valid
    SAML Assertion의 유효 시간이 이미 지난 것으로 판정되고 있었습니다. 확인해 보니 모니터링 서버는 시간 동기화가 되어 있었지만 Keycloak 서버는 시각이 어긋나 있었습니다. 서버 간 시간을 동기화하자 정상 로그인됐습니다.

배운 점

  • 서버 간 시간 동기화는 연동의 기본 전제입니다. SAML처럼 인증 정보에 유효 시간을 담아 검증하는 방식은, 서버끼리 시각이 조금만 어긋나도 정상 요청을 만료된 것으로 판정합니다. 화면이나 일반 로그에는 원인이 드러나지 않아 가장 찾기 어려웠던 문제였습니다.
  • Nginx가 HTTP 응답을 중계할 때 쓰는 버퍼에는 크기 한계가 정해져 있고, 설정으로 늘릴 수 있습니다. 응답 헤더가 기본 버퍼(proxy_buffer_size)보다 크면 Nginx는 응답을 전달하지 못하고 502를 반환합니다. 이 경우 proxy_buffer_size, proxy_buffers, proxy_busy_buffers_size를 키워서 해결할 수 있다는 것을 배웠습니다.

CASE 03

Go APM 자동 계측 도구 검증 — 옵션 버그 발견

2026.11APM 솔루션 엔지니어Go 애플리케이션 고객사 지원
  • Go
  • Gin · Echo · Fiber
  • GORM · sqlx
  • gRPC · Kafka
  • 자동 계측

결과 — 빌드 래퍼 방식 자동 계측 도구를 검증하다가 --error-tracking 옵션의 비정상 동작을 발견했습니다. 벤더가 이를 제품 버그로 확인했고, 수정 전까지 해당 옵션을 쓰지 않도록 고객사에 미리 안내했습니다.

상황

Go APM은 whatap-go-inst go build처럼 빌드 명령을 감싸서, 컴파일할 때 모니터링 코드를 주입하는 방식입니다. 고객사가 실제로 쓰는 프레임워크와 라이브러리에서 계측이 잘 되는지, 옵션별로 어떻게 동작하는지 확인이 필요했습니다.

검증 과정

  1. 검증용 애플리케이션 구성 — 웹 프레임워크 6종(net/http, Gin, Echo, Fiber, chi, gorilla/mux), DB 접근 4종(database/sql, sqlx, GORM v1/v2), Redis, MongoDB, gRPC, Kafka(sarama), Kubernetes client 등 17개 의존성을 넣은 샘플 앱을 만들었습니다. go build, go test, remove 명령으로 계측 대상 파일과 결과를 하나씩 확인했습니다.
  2. 문서와 실제 동작의 차이 정리 — 문서에 있던 inject 명령은 이미 제거됐고, 설정 파일의 preset 항목은 현재 버전에서 지원하지 않는다는 점을 확인해 정리했습니다.
  3. 이상 동작 발견 — 에러 추적 코드를 자동으로 주입하는 --error-tracking 옵션을 켜면 빌드가 실패하고 계측된 파일이 0개였습니다. 
    $ whatap-go-inst --error-tracking go build -o app .
go: error obtaining buildID for go tool compile: exit status 1
📁 Total: 0 files
  4. 같은 코드에서 옵션만 빼면 정상이라는 점과 재현 절차를 정리해 벤더에 문의했고, 벤더가 제품 버그로 확인했습니다.

배운 점

설치 가이드를 그대로 전달하기 전에 고객사 기술 스택과 비슷한 환경에서 직접 돌려보는 것이 장애를 예방하는 가장 확실한 방법이었습니다. 동작 여부는 문서가 아니라 실제 빌드 결과와 로그로 판단했습니다.

CASE 04

고객사 재현용 폐쇄망 테스트 환경 구축

2026APM 솔루션 엔지니어사내 테스트 환경
  • Rocky Linux
  • Kubernetes
  • Harbor
  • Docker
  • Prometheus

결과 — 외부망이 차단된 폐쇄망 고객사가 많아서, 비슷한 조건의 테스트 환경을 직접 구성했습니다. 고객사에서 생긴 문제를 사내에서 먼저 재현하고 검증한 뒤 대응할 수 있게 됐습니다.

구성한 것

  • 컨테이너 레지스트리(Harbor 2.14) — 외부망 레지스트리를 쓸 수 없는 환경을 가정해 사설 레지스트리를 구축했습니다. 설정 파일 전체를 항목별로 분석해 문서화했고, 이미지 취약점 스캐너(Trivy)를 폐쇄망에서 쓰려면 어떤 옵션이 필요한지도 정리했습니다(skip_update, offline_scan).
  • Kubernetes 테스트 클러스터 — 클러스터를 구성해 컨테이너 모니터링 에이전트 배포를 실습했습니다. 특정 노드에만 DaemonSet을 배포하는 방법과 kubeconfig 인증서 오류 해결 과정을 정리했습니다.
  • 오프라인 패키지 설치 절차 — 외부망이 되는 곳에서 의존성까지 내려받고(dnf --downloadonly), 폐쇄망에서는 저장소를 끈 채 설치하는(localinstall --disablerepo=*) 절차를 만들었습니다.
  • Keycloak SSO 재현 환경 — Docker Compose 기반으로 구성했습니다(CASE 02).
  • OpenMetrics 수집 검증 — Prometheus 형식(OpenMetrics)으로 노출되는 메트릭을 수집하는 파이프라인을 만들고, 모니터링 에이전트로 연동되는지 확인했습니다.

일하는 방식

설정 파일과 명령마다 "이 옵션이 왜 필요한지"를 주석으로 남겨 팀이 함께 쓰는 문서로 만들었습니다. 설정 초안을 쓸 때는 생성형 AI를 활용했고, 실제 실행 결과와 오류 로그로 검증한 뒤 수정했습니다.

CASE 05

개발 프로젝트

2024.06 ~ 2025.07백엔드 개발
  • 데이터 마이그레이션 SQL 생성 자동화 — 작업 시간 약 85% 단축 대형 가전 기업 해외 사이트 구축(AEM). 약 200개 테이블, 30~40만 건을 이관하면서 엑셀 함수로 만들던 INSERT 문을 Java 메서드로 자동 생성했습니다. 테이블당 약 20분 걸리던 작업이 3분으로 줄었고 수작업 오류도 없앴습니다. · 상세 글

  • 알림 플러그인 개발 (Java) 모니터링 서버의 알림 플러그인 구조를 활용해 Slack API와 SMS 알림을 구현했습니다. 고객사 요구에 맞춰 특정 이벤트만 별도 경로에 기록하는 플러그인 방안도 설계했습니다.
